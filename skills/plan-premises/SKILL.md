# Plan Premises

Plan-time verification rules relocated from `~/code/CLAUDE.md` and
`~/code/games/CLAUDE.md` on 2026-07-28. Every entry is a rule earned from a
specific failure; the dated citation is why it exists and is part of the rule.

Read this before writing or reviewing any plan or checklist. A plan that skips
these checks ships premises as facts — the documented primary cause of wasted
iteration cycles in this workspace.

## Universal

**Plan path verification:** Every file path listed in a plan must be verified to exist (Glob) at plan-writing time — stale grep results are not evidence.

**Derivability is a premise about TOOL OUTPUT, and it gets executed at plan time like any other premise.** A step of the form "X is derivable from `<command>`, delete it" is checked by pasting the command's ACTUAL output and diffing it against the text being deleted — never by reasoning about what the command probably prints. This premise class carries a hazard a bad file path does not: a bad path fails loudly, but a tool can answer confidently and WRONGLY, so deriving swaps a true rule for a false one with every gate green. (2026-07-28 context-restructure T14: both derivability claims false — `ls src/` reproduced no annotations or conventions, and `just --list` emitted a stale `e2e` description flatly contradicting `playwright.config.ts:30`. Issue #10.)

**An exemption is never the first response to a red zero-loss / parity gate.** Ask "is the deletion right?" before "how do I record the deletion?". A gate firing on a plan step is evidence about the PLAN, not a defect in the gate. Reaching for exemption machinery first launders a genuine loss through an audit trail that reads as honest — a cold reviewer independently proposed exactly that here (correct machinery, false premise), and executing the underlying premise instead retired the blocker with zero new exemptions. (2026-07-28 context-restructure T14.)

**A wave whose deliverable is a PROCESS or CONTEXT change gets a cold-session plan review BEFORE execution.** The author cannot audit their own premises — to the author they are invisible AS premises — and the wave's gates are built from those same premises, so the gates cannot catch them either. Hand a fresh session the plan and ask for defects, with no summary of intent. (2026-07-28 context-restructure: one cold review of two tasks returned 7 real defects, none self-caught, including a live rule being relocated into a file nothing loads and a cwd/path collision that would have committed into the wrong repo. Cost: one prompt. Issue #11.)

**A presence check is not a reachability check.** When a plan MOVES a rule, "the text exists at the destination" is only half the verification — the other half is that something actually loads that destination. A rule relocated into an archive, a history file, or an un-junctioned directory is lost exactly as thoroughly as a rule deleted, and a text-presence gate passes it. Verify the destination is on a load path for the situation the rule governs. (2026-07-28 context-restructure T14: an active workflow rule was relocated into `docs/WAVES.md`, a history file nothing loads; `verify-relocation.mjs` passed it correctly by its own definition. The wave violated its own thesis and its own gate could not see it.)

**A wave that introduces N model-invoked routing surfaces probes ALL N, plus a NEAR negative control, and defines the remediation ladder BEFORE any probe runs.** Probes are one prompt in one fresh session; the expensive part is finding a dead pointer three weeks later, when the rule it guarded was needed. Four properties make a probe worth its prompt, and all four are cheap only if they are decided in advance:

- **Uncontaminated prompt.** A probe that states its own pass criterion measures nothing — an early run put "watch for X" in the prompt and had to be discarded as unattributable. Paste the prompt verbatim with nothing added.
- **Never answerable from disk.** An existence probe is contaminated by the FILESYSTEM: a session asked "is skill X available" greps the skills directory, finds a folder, and reports a pass that proves only that a folder exists. Forbid disk access in the prompt, and adjudicate outside the probe against a list captured beforehand.
- **A NEAR negative control, not just a far one.** The control that earns its keep sits inside the target skill's APPARENT topic and outside its real one (a Tailwind spacing tweak vs a brand/asset skill). A far control passes trivially and proves comparatively little; without a near one, N fires prove sessions load skills, not that they load the RIGHT ones.
- **A pre-committed expectation table and verdict vocabulary.** PASS / MISS / CONTENT WIN / CO-FIRE, with a per-probe discriminator written down first. Discriminator absence is what separates a MISS from a CONTENT WIN — real value delivered with zero routing evidence — and that distinction is not decidable after seeing the answer.

Remediation ladder, in order, one attempt per rung, at most three fresh sessions per missed skill: **rung 0** re-probe from a cwd outside the `CLAUDE.md` chain (diagnostic — isolates the pointer and rules out context starvation); **rung 1** rewrite the skill's `description`; **rung 2** rewrite the Tier-1 pointer; then TERMINAL, routed by rule type — mechanically checkable → PreToolUse hook, judgment rule → promote back to an always-loaded file. Rung 0 first even when the fix seems obvious: it is what makes the fix transferable rather than a one-off. (2026-07-28 routing-verification: 6 probes, 5 PASS, 1 MISS resolved at rung 1 — and rung 0 is what proved the pointer was the wrong lever, so rung 2 was correctly never reached. See SKILLS.md §Writing a Skill `description` for what the miss taught.)

**Addendum 2026-07-28 (description-audit) — the ladder's first failure, and two amendments.** Applied to `live-qa-traps` and `games-diagnostics`, the ladder ran out: rung 0 MISS, rung 1 MISS, 10 fresh sessions, no false fire on either near control. (a) **The session cap outranks the rungs.** The 3-session budget was spent at rung 1, leaving rung 2 unreachable by the ladder's own arithmetic, and the ladder said nothing about which governs. It does now — at the cap, stop and escalate to the user rather than borrowing sessions; the cap exists precisely to stop the "one more wording tweak" spiral that a failed rewrite invites. (b) **Before spending a rung on a rewrite, diff the proposal against a description already known to pass.** That comparison is free and needs no session. Running it only AFTER rung 1 failed is what cost this wave four user-run probes: it produced the diagnosis that the passing description enumerated concrete artifact nouns while both failing ones led with an abstract category the session must classify its own work into — which would have changed the rewrite had it come first. TERMINAL here was promote-the-trigger, not a hook: the rules are judgment rules, and the trigger moved to an always-loaded file while the bodies stayed in their skills.

**A session cannot probe its own routing.** Observing the effect contaminates it — the probing session already knows what it is testing for. Every probe is a fresh session the user runs, which also means probes cannot be parallelized away to subagents.

**Relocated rule text is append-only in practice.** Once a wave freezes a baseline, the zero-loss gate matches those paragraphs byte-for-byte wherever they landed — so editing a relocated rule (adding a bullet to its block, updating its `n=`) reads as MISSING, identical to deleting it. Update by appending a dated addendum next to it; rewrite only with an `INTENTIONAL_EDITS` entry stating what was verified by other means. Worth knowing at plan time, because "we'll just tweak that rule later" is now a two-step operation. (2026-07-28 routing-verification reflect, issue #8.)

**Parallel-cluster annotation:** writing-plans marks genuinely independent task clusters explicitly (`**Parallel-safe with:** T4, T5` — no shared files, no Consumes/Produces edge between them); agent-factory may worktree-parallelize ONLY annotated clusters. No annotation → serial default. Windows worktree overhead (removal fights, per-worktree install, gate CPU contention) makes speculative parallelism a net loss — gates dominate wall-clock, not agent count. (2026-07-16 w3L: strict dependency chain, parallelism worth zero.)

**Plan-embedded verbatim code must be prettier-clean AND TS-style-clean** against the target repo's config at plan-authoring time (check `.prettierrc` — quotes, semis, trailing commas — and the four TS-style rules, explicit return types on exported functions especially). A byte-for-byte implementer faithfully reproduces the drift; it surfaces only at the full gate run or review. **Two more plan-time checks on verbatim blocks (2026-07-26 oauth wave, 2+2 instances in one wave): (a) tsconfig strictness flags** — `noUncheckedIndexedAccess` especially; plan destructure/index patterns illegal under the repo's flags forced 2 sound-but-avoidable deviations; **(b) verbatim code+test PAIRS need branch parity** — every branch the code block carries must be exercised by its paired test block (json-parse fallbacks and negated-condition paths are the usual misses); under 100%-coverage gates an unexercised branch is a guaranteed review Major, hit twice in one wave (T1–4 Minor, T7–8 Major → warm redo). (2026-07-15 w16: plan-authored test + story + README table cost a full gate rerun. 2026-07-21 motion-pass T6: plan block's missing return type shipped byte-faithful, flagged as review Minor.) **Tailwind-class-sorted too** when the repo runs prettier-plugin-tailwindcss, and asset-copy instructions ("byte-identical copy of X") state the FORMAT AUTHORITY — which side gets prettier-formatted — or identity and the gate conflict (2026-07-24 carsickyak W1: both facets in one wave; resolution = format the docs source, recopy). **Plan-cited utility classes are premises about the repo's token config** — grep tailwind.config at plan time; an undefined utility emits NO CSS and every gate passes silently (2026-07-24 carsickyak T10: `bg-charcoal/60` scrim on an undefined token — invisible scrim, coverage/tsc/axe all green).

**Port/generalization waves inherit the source's bugs:** byte-faithful porting preserves the source's defects — parity review + 100% coverage structurally cannot catch them. The wave's QA step must drive the FEATURE's semantics live (all-day = which day? what persists?) plus the repo's documented trap list (close→reopen, create-after-create), not just port parity. And shell-extraction plans must diff ALL form/container attributes across EVERY source being generalized, never just the primary reference. (2026-07-22/23 slot-W2: user-caught all-day null-instant bug was the DELETED source dialog's own bug shipped through green gates; `noValidate` was a one-attr diff between the two sources — cost a mid-wave patch release. Issues #4/#6.)

**Deferred-gate plans give intermediates a scoped probe:** a plan that defers a repo-wide gate (tsc especially) across tasks masks NEW-file errors until the gate task — intermediate tasks producing new files need a scoped typecheck substitute, or the gate task's brief must explicitly own new-file errors, not just rewire errors. (2026-07-23 slot-W2: A2/A3 shipped 12 strict-null errors invisible to vitest, surfaced at A4; issue #5.)

**A correction made to a plan DURING the session it is executed needs a grep for every consumer sharing the corrected premise — not just the one that prompted it.** A correction feels applied the moment it is written, and the authoring session is exactly the session least able to see the second consumer. This is cheapest to catch at correction time; the alternative is a warm redo mid-dispatch. (2026-07-28 dog-eat-dog QA-R2b: a day-speed-band correction written that same session was applied to one of the two tests that needed it. The other asserted a weaving-beats-holding property against a free band, where fast rolls pack the walls to ~35 units against a ~55-unit weave cost — weaving genuinely cannot win. Two seeds caught it; the plan could not have been read into catching it.)

**A test constant whose comment claims it mirrors config must READ config.** The comment is true when written and rots silently, and the failure surfaces as property tests failing for a geometry that no longer ships — a diagnosis that looks like the change broke something rather than like the tests going stale. (2026-07-29 dog-eat-dog QA-R2e round 2: `test_lane_sim.gd` hardcoded `_ROUTE_LENGTH := 400.0` under a comment reading "the shipped commute numbers … so the skill properties are asserted against what the player actually drives." It was a COPY; the route had moved to 900 and three property tests failed. Now `BalanceConfig.new().drive_length`.)

**Addendum 2026-07-29 (dog-eat-dog QA-R2c) to the plan-premise-verification rule below — a Godot instance of it.** A plan block that consumes a `Range`-derived node's `.value` (`ProgressBar`, `Slider`) is a premise about that node's `max_value`, and `max_value` lives only in the `.tscn`. The default is 0–100, so arithmetic written against a 0–1 fraction is silently wrong wherever the scene didn't override it. Verify in the scene file at plan or dispatch time. (`drive.tscn:49` sets `max_value = 1.0`, so the plan's `route_miles * (1.0 - _progress.value)` was right; at the default it would have read `9.0` for the first percent and gone negative after — in a display-only surface no test asserts numerically.)

**Plan premise verification:** Any plan step that says "follow the existing pattern in X" must cite a verified `file:line` confirmed at plan-writing time. **An "import X from Y works" premise is verified per CONSUMER TOOLCHAIN, not per package** — bundler/runtime aliasing, tsc types, and test-runner resolution are three separate facts that can disagree. (2026-07-21 motion-pass T7: plan asserted `import { ViewTransition } from 'react'`; true under Next's vendored-canary alias, false under tsc (stable @types) and vitest (real node_modules/react) — implementer NEEDS_CONTEXT'd with zero edits; resolution = canary-types d.ts + per-test partial react mock.) Unverifiable premises are written as assumptions to confirm, never as facts. (2026-06-10: a plan asserted e2e session mocking existed — it didn't; cost a full task to deferral.) **An e2e plan step must verify the SUITE CAN OBSERVE the target surface at plan time** — auth model, server-side redirects, mocking capability. n=2: the 2026-06-10 case above; 2026-07-24 event-series A10 — unauth suite asserted to render authed surfaces, but the server-side auth redirect makes them structurally unobservable; step dead on arrival (issue #6). A premise about a library component's runtime behavior must trace the FULL wiring chain (view → leaf), not just leaf-level gates — a leaf gate plus unconditional parent wiring inverts the conclusion. This binds dispatch briefs too, and "prop threads through" claims specifically: trace the intermediate wrapper, not prop existence at both ends. **And it binds SPEC/BRAINSTORM-time claims** — a brainstorm-quick dist read verifies the paths it looks at, not the component; full-surface recon before spec claims, not just before plans. (2026-07-15 user-profiles: chip-level lock gates verified, view-level unconditional handler wiring missed → "fully inert read-only chips" premise shipped false; caught only at Task 9 doc verification. n=2 2026-07-20 w3 A12: orchestrator brief premise from a leaf-only dist read — view constructed an always-defined wrapper, leaf gate alone inert; implementer TDD'd its way to the wiring bug. n=3 2026-07-24 visibility-w1: spec's "zero-handler WeekCalendarView = read-only for free, no lib wave" premise false — chip wiring unconditional; plan recon caught it, wave shape changed to lib-patch-first.)

**Measured numbers entering a diagnosis brief are premises — verify each two independent ways before writing it as fact.** A single-method measurement can be systematically wrong (sampling stride aliasing with a buffering window; a feel-bar calibrated against the wrong reference), and a faithful diagnostician downstream builds on the bad number. n=2 in one wave (2026-07-24 momentum-lab: R12 turn-rate bar miscalibrated vs CS-at-equal-speed; R13 stride-2 telemetry samples phase-locked onto a 2-tick drain window → reported −57°/s where position-delta truth was −118.8°/s — convicted a phantom engine bug, cost a full diagnosis round). Rate/derivative measurements specifically: compute from POSITION deltas over the span, never from stride-sampled per-tick deltas when the stride shares a factor with any pipeline buffering window.

**Live-state enumeration is a plan premise too:** a plan that enumerates live working-tree state (worktree registrations, dirty files, loose root artifacts, branch positions) re-verifies that enumeration at execution start — design-time recon is an assumption, not fact; concurrent sessions invalidate it. Prefer fail-fast steps (explicit-path commands that error loudly on a missing path) over silent re-capture. (2026-07-21 restructure w1: plan enumerated 5 worktree registrations at design time; a concurrent PR merge left 1 by execution — the fail-fast `git status` on an enumerated path caught it.)

**Addendum 2026-07-28 (settings-tabs) — the verbatim-block rule extends to the repo's LINT RULE SET, and it binds SPEC-embedded sketches, not just plans.** Formatting, TS-style, and tsconfig flags are three of four premise classes a code block asserts; the fourth is which lint rules the repo has turned into errors, and that set is per-repo. A spec sketched hash-seeding as a mount effect, which is a hard `react-hooks/set-state-in-effect` ERROR in this repo — and the obvious fix, a `useState` initializer reading `window`, is the same repo's documented hydration trap. Both were caught only because a draft was run through the repo's real eslint before entering the plan; the rule as previously written did not require that. Cost of the check: one scratch file, three commands. Cost of missing it: the red TDD step is already written against a shape that cannot compile clean, so the redesign lands mid-TDD instead of at spec time. Write plan/spec code blocks, then run the repo's actual `prettier --check`, `eslint`, and `tsc --noEmit` over them before they are pasted into the document. (Issue #1.)

**A brainstorm choice whose options differ by a QUANTITY is provisional until the first live QA, and the spec says so.** Structure choices made against ASCII mockups hold: settings-tabs took scroll-to-section over panel-swapping, three tabs over four, sticky over static, all from previews, and every one survived hands-on QA untouched. The single choice that came back was the one whose difference was a *number* — "just enough space that the last section can reach the top of the viewport" reads as a reasonable rule in text and as dead space in a browser, because a mockup conveys STRUCTURE faithfully and MAGNITUDE not at all. So: when the options in an AskUserQuestion differ by spacing, duration, density, size, or count-as-feel, record the pick in the spec as settled-in-kind and provisional-in-degree, with the revisit point named (first live QA). This is cheap to state and changes what the correction MEANS when it arrives — an expected tuning pass rather than a defect. Watch for the coupled-change tail: shrinking the settings spacer invalidated the scroll-spy's whole premise (a small spacer can never lift the last section into the spy band), so the quantity change forced a behavior change one task later. (2026-07-28 settings-tabs issue #4. n=1, provisional — the falsifiable claim is that quantity-choices regress and structure-choices do not.)

(w3 2026-07-16→20: SIX misses in one wave — activity-card-actions, quick-schedule-input, action-confirm-card, profile.ts+reflection-card+layout.tsx at teardown, generation.ts entry point, chip component for the Duplicate action; two were in orchestrator dispatch briefs, not plans.) **Invariant-consumer enumeration:** A plan task that CHANGES a cross-cutting invariant (time semantics, data shape, ordering) must list every consumer of that invariant — including observability/validation nets (drift checks, assertions), which are read-path consumers too. Per-task reviews structurally cannot see a task invalidating an earlier task's net. (w2.6: S12 made generation TZ-aware; S8's drift net still compared UTC time-of-day → DST false positives, caught only at final whole-branch review.) **Changing what a predicate MEANS counts as changing the invariant** — n=2 (2026-07-24 event-series #4): standalone series made `activityId IS NULL` no longer mean "one-off"; the query consuming that predicate (`getStandaloneEvents`) was never enumerated, occurrences double-rendered through 100%-green gates. Mitigation that worked: a reviewer probe that NAMES the invariant ("activityId IS NULL = one-off") gets its consumers traced — the A6 reviewer chased the INSERT path cross-module and caught it.

**Invariant adoption audit:** When an invariant is adopted into a repo's AGENTS.md (e.g. "times are local wall-clock"), audit ALL code paths against it at adoption — write/generation paths, not just the read paths whose bugs prompted it. (w2.6 QA-R2: local-wall-clock invariant fixed read paths in 0.19.0; UTC-day series generation stayed latent until an evening-created series shifted a whole day.)

**Value-judgment UX semantics get a user pick at spec time:** any behavior encoding a product-feel judgment (streak projections, motivational displays, optimistic vs confirmed states, gesture-release motion — how a drag/snap/dismiss FEELS, not just where it lands) is presented as an explicit spec question, never buried as a plan walk-rule. Built-and-reviewed-green is worthless if the user rejects the semantics on first sight. (w2.6: S2 future-chip flame projection rejected wholesale at QA R2, rebuilt as S13. n=2 2026-07-22 slot-w1 T13: spec fixed the snap TARGET corner, never the release feel — instant jump rejected at QA, rebuilt as animated glide. n=3 2026-07-22 gs-p1: "command palette" framing buried the modal-vs-inline-dropdown PRESENTATION choice — modal rejected on first sight, whole shell rebuilt in QA-R1; a feature's presentation pattern is this class too.) Fallback-surface AFFORDANCES are this class too: an error/empty/loading state's action set (retry only? home link? support contact?) is a spec question — enumerate it when the spec introduces the fallback, per boundary level (a root/global boundary strands the user; a segment boundary keeps nav). (2026-07-16 eb3: home-link gap user-caught at ship gate; whole rollout shipped retry-only.) **Theme DEFAULT (which theme greets a first visit) is this class too** — a multi-round palette gate on rendered candidates never asks it, and per-surface entry affordances (is the preview card itself clickable?) ride along; copy accepted on a corpus/acceptance page gets re-judged in live page context at QA. (2026-07-24 carsickyak W1 QA-R1: spec'd light-first reversed + accepted motto pulled + teaser cards made clickable, all in the user's first hands-on minute; n=1 provisional.)

**Live-dev migration sequencing:** When a wave adds or renames DB columns that a running dev server reads, the migration applies in the SAME task that lands the schema change — otherwise every authenticated page 500s from that task until the migration task runs. (Wave 2.3: schema landed at S3, migration was planned at S6; user hit `column does not exist` browsing dev.)

**Gated-consume API assumptions:** When a plan consumes a dependency version that does not exist yet at plan-writing time (publish-gated waves), every API name taken from the spec or memory is written in the checklist as an ASSUMPTION and verified against the installed dist at the first dispatch after the dependency publishes — never treated as fact. (cybond w2.4: checklist + brief carried `onToggleLock` for the view-level prop; 0.19.0 shipped `onEventToggleLock`; cost a warm redo, 2026-07-08.) **A bump crossing intermediate releases must also diff the installed-vs-target export surface** (`dist/index.d.ts` export list, old vs new) at the bump step — the bump consumes EVERY intermediate release's breaking changes, not just the wave's own additions; verifying only the wave's new API names passes while removed/renamed exports break tsc app-wide. File-overlap checks against concurrent branches don't catch this — the coupling is the library surface, not files. (2026-07-17 eb4 w4d: 0.22→0.24 bump verified `homeHref` present, missed 0.23.0's `Activity*`→`Event*` rename; cost a full implementer dispatch to discover, wave sub-task deferred.)

**Belt-and-braces check — of every pair of mitigations aimed at one goal, ask: does the belt stop the braces working?** Two defenses against the same risk are not automatically additive; one can destroy the other's precondition, and the plan then ships something that reads as doubly-safe and is in fact worse than either half alone. **The tell is inside the plan text, needing no external knowledge: a step that states a precondition and then specifies something violating it is self-refuting on its own terms.** The AdSense W1 case: `robots.txt` `Disallow: /` plus a `X-Robots-Tag: noindex` header, with the step's own prose correctly noting that noindex "must remain crawlable for Google to see the header" and concluding "both are required; neither is redundant" — the two halves of that sentence contradict, since Googlebot never fetches a disallowed URL and so never receives the header. The failure mode is worse than a no-op: the host was already live and possibly indexed, and Disallow freezes an existing index entry permanently because recrawl can never discover the noindex. **Verify each half's precondition against the other half, not just each half against the goal.** (2026-07-28 AdSense W1 issue #8, caught at execution — the plan review had passed it.)

## Games

Godot-specific plan-time checks. The universal rules above apply too.

- **Respawn/reset math verified at BOUNDARY markers (first/last) at plan time.** A zero-floor progress clamp + `>=` catch check = infinite instant-recatch at marker 0 — shipped in plan-verbatim code, structurally uncatchable by per-task review, found only in playtest. (what-is-dark T7, 2026-07-22.)
- **Completion-threshold accumulators get a plan-time exactness trace** — any `progress >= 1.0`-style check over summed fractional increments (`1.0/target` per press) never fires at the exact boundary (0.1×10 = 0.9999…); count whole events in an integer/float counter and derive progress instead. Same float-boundary class as the marker rule above, different site: plan self-review checked boundary markers but not the accumulator. Caught pre-merge only by implementer NEEDS_CONTEXT. (dog-eat-dog T4 issue #1, 2026-07-24.)
- **Screen-covering / volumetric visuals get a "camera inside it" pass**, not just distant-view — a paper-thin QuadMesh void wall showed the unswallowed world at camera contact during the swallow fade. (what-is-dark T7, 2026-07-22.)
- **"Auto" traversal mechanics (auto-vault, auto-step, auto-climb) are spec-time user questions, never plan walk-rules** — auto-vault shipped built-and-reviewed-green and was cut on first play. Games instance of the universal value-judgment-UX rule. (what-is-dark T4, 2026-07-21.)
- **Difficulty bands state their FAILURE MODEL at spec time** — margin-first ("always makeable with slack") vs commitment-first ("clear only at full execution"); spec-HARD in a speedrun game = commitment-first. And bands calibrate against the FULL movement capability envelope including compound chains — measure each verb in a lab env (wall-jump chain measured 196 m/24 m where the single-arc model predicted a horizontal slide), never derive from single function calls. (what-is-dark phase 2: zones 1 AND 2 shipped "way too easy"/"incredibly easy" n=2; chain miss forced a mid-wave lab + shell retrofit, 2026-07-22.)
- **Director/tween sequence PAIRS get an overlap trace at plan time** — for every pair of concurrent sequences (swallow × loop, fall × anything), trace "the other fires mid-window" against the tween-callback timeline. "Same frame" claims about tween callbacks are false by construction — callbacks run at step END. (n=2: what-is-dark phase-1 T7 respawn, phase-2 T3 loop-credited-during-catch — both plan-authored, caught by review/playtest.)
- **A day-cycle event's placement in the day arc (which slot, before/after what) is a spec-time user question, never a plan walk-rule** — rank-ladder news placed in the day-end summary read as "promoted in the morning, in bed"; user ruling moved it to a same-day office beat after afternoon work. Same value-judgment class as the wobble telegraph: when a wave adds day-cycle events, WHERE each lands is spec input. (dog-eat-dog w2 issue #9, 2026-07-26. n=1, provisional.)
- **A new mechanic's showcase placement + pacing is spec/plan-stated, never implementer latitude** — spacing across zone structure (mid-zone, one per zone-half) and rhythm (rest beat BEFORE the hard section, short re-entry after — the breather is preparation, not reward). Free latitude converges on clustering: flat-stretch availability correlates across zones (seams are flat). (what-is-dark phase-2 T5c/T5d/T5e: corridors clustered at the seam, then pacing inverted — two relocation rounds, n=2 in one wave, 2026-07-22/23.)

**A constraint set that enumerates CATEGORIES must be exhaustive over the game's verbs, or geometry crossed by the missing verb is audited by nobody.** The categories are what the audit iterates; anything outside them is not "failing" — it is invisible. State the audit obligation per category, not just the category. (what-is-dark 3b #32: the constraint "every gap above 8.31 m states its required carried speed" had exactly two categories — bare-run and carried-speed — so two 8.50 m D3 gaps designed to be crossed by wall ride matched neither and appeared in no census, including the zone task's own. The geometry was sound and the walls were there; the bookkeeping had no row for them. The missing third category was "crossed by wall ride", whose obligation is a wall span-and-extent budget, not a speed.)

**A verbatim FK column in a plan copies the type of the REFERENCED column, not the new table's own pk convention.** New-table blocks are written in one idiom (`uuid('id').primaryKey().defaultRandom()`) and the FK lines inherit it by reflex, which is wrong wherever the referenced table predates that convention — Auth.js `users.id` is `text`, so every user-FK in the repo is text. Postgres rejects the mismatch only on real apply, so plan review, tsc, and a dry read all pass it. Check the ripple in both directions before "fixing" it upward: the VALUES were uuid-format strings, so a `z.string().uuid()` validator downstream stayed correct. Side casualty worth planning for: the failed first apply leaves a broken empty table on the dev DB, and cleanup is destructive DDL. (2026-07-26 friends-w1 issue #4, T1 — implementer caught it with the real Postgres error.)

**Addendum 2026-07-29 (friends-w1 issue #3, n=4) to the value-judgment-UX rule above — a NEW page surface has a presentation ARCHETYPE, and it is a separate spec question from the surface's structure.** The friends plan specified structure completely (three sections, copy, empty states) and was rejected on sight mid-QA — "should feel like a typical social media followers page" — costing a full re-layout as an appended task. Entry-point and parity enumeration (the new-page-surface rule) does not reach this: both were done. The cheap tell is the surface's name. If it has a well-known consumer-app archetype — followers list, inbox, feed, settings, gallery — name the archetype in the spec, or ask with rendered options. Users judge a page against the archetype they already know, and that comparison happens in the first second of QA, before any of the structure is read.
